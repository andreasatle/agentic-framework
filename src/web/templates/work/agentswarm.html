AgentSwarm is my answer to what went wrong in my earlier agent frameworks. In Forge, a planner, a worker and an LLM critic depended on each other's output in a fixed order. Roles ended up waiting on each other, the plan-then-execute split was too rigid, and every verdict was a full LLM call with a self-reported "confidence" that nobody had checked.

The design

Independent teams (an executor, an integration tester, a red team, a planner, ...) each watch one level of a shared, append-only blackboard. They never call each other. Each one reacts to the current state of the project, the way a Kubernetes controller reconciles desired and actual state. Because no team waits on another, there is nothing to deadlock.

Work products are git branches, and they mature through levels. To move up a level an artifact has to pass a gate: deterministic checks first (tests, builds, scanners), then a few narrow yes/no questions answered by Jev, a small decision model that returns a probability rather than prose.

rawA branch per task. An executor writes code and tests in a Docker sandbox with no network.
experimentalGate: tests, then Jev on complete, in scope, tested.
candidateA release train. Integration testers and red teams attack what has merged.
productionThe last gate can require a person, configurable per project.

The split of responsibility is the core rule. Language models produce code, text, tests and plans. Jev decides whether something is in scope, good enough, or drifting. Plain code controls everything that has to be reliable: claims, merges, budgets and scheduling. Everything is typed with Pydantic end to end, and every model-backed part has a fake, so the whole system runs offline and deterministically in tests.

A judge that is measured, not trusted

Every decision Jev makes is logged and later scored against what turned out to be true. Evaluation suites provide that truth automatically: hidden tests, mutation testing and planted faults. From the log, agentswarm calibrate reports reliability per question (ECE, Brier score), tune picks pass/fail thresholds that reach a target precision, and audit checks the active gate's false promotions, false rejections and escalations against fixed bounds using Wilson intervals.

Jev starts in shadow mode, logged but never blocking, and only gets to act at a gate once its numbers earn it. So far the active gate made 1 false promotion in 41 overall and 0 in 16 on held-out tasks. That isn't enough data yet: the 95% upper bound reaches the 5% target only after about 73 clean promotions, so proving that is still an open item.

One engine, several domains

Software and documents are configurations, not separate code. The same engine writes a handbook through draft → reviewed → final → published, with reviewers whose every complaint must quote the text. A swarm runs several projects side by side under one scheduler, each with its own daily budget.

What I'm working on now

  • Acceptance checks the producer can't write or change. Outside the evaluation suites, the gate runs the tests the executor wrote for its own work, and a model that writes weak tests passes. A separate team now writes acceptance tests from the task before the executor starts. They must fail on the current code, and plain code restores them if the producer touches them.
  • The goldilocks question. The hypothesis behind the project is that many small, narrow agents can match one bigger model, because the structure asks less of each call. The comparison runs the same task suites under different setups (one big model, one small model, a tiered setup, a full swarm of small models), all scored by hidden tests, with cost in tokens and time.
