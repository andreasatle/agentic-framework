Why run a coding model locally, and the one number that decides everything

This tutorial uses 'local coding model' to mean an open-weight model that runs on your own GPU or unified-memory machine, is served by an inference engine, and is called by an editor or an agent. The first question is not which brand to buy but how many bytes the model needs, because that number decides which hardware is eligible1. At batch size 1, decoding reads nearly all model weights for every generated token, so it is memory-bandwidth-bound and compute sits idle1. A 70B model at 4 bits stores 0.5 bytes per parameter, about 35 GB per token; 800 GB/s divided by 35 GB gives a ceiling of about 22.9 tokens/s1. The practitioner measured about 12 tokens/s on a Mac Studio M2 Ultra, roughly 53% of that ceiling1. The roadmap covers memory arithmetic, quantization, engines, efficiency techniques, integration, evaluation, trust and model choice. The bandwidth ceiling and memory formulas are derivations, while the prices and measured speeds come from one practitioner blog1.

Hardware: memory arithmetic, bandwidth and what it costs

Before any engine or model is chosen, the reader needs one number: how many bytes the model occupies once loaded1. The blog treats hardware selection as a sequence that starts from model size, not from brand or budget1.

The blog gives the memory of weights as parameters times bytes per parameter, namely 0.5 bytes for 4-bit and 1.0 byte for 8-bit weights1. Writing \(P\) for the parameter count and \(b\) for the bits per weight, the rule is as follows.

$$ M_{\text{weights}} = P \times \frac{b}{8}\ \text{bytes} $$

For a 32B model, 16-bit weights need \(32\times10^9 \times 2 = 64\) GB, while 4-bit weights need \(32\times10^9 \times 0.5 = 16\) GB. The blog's own figure is that a 32B model can take 60+ GB in its default form2. The 16 GB and 64 GB figures are this section's arithmetic and exclude the KV cache.

At batch size 1, each generated token reads essentially all active weights from memory while doing little compute, so decoding is bandwidth-bound in the Roofline sense1. If \(B\) is memory bandwidth in GB/s and \(W_{\text{tok}}\) is the bytes read per token in GB, the blog's ceiling is bandwidth divided by model bytes in GB1. For a mixture-of-experts model, only the active parameters \(P_{\text{active}}\) are read per token1.

$$ \text{tokens/s} \lesssim \frac{B}{W_{\text{tok}}}, \qquad W_{\text{tok}} \approx P_{\text{active}} \times \frac{b}{8} $$

For a 70B model at 4 bits, \(W_{\text{tok}}=35\) GB, so an 800 GB/s Apple M2 Ultra has a ceiling of about 22.9 tokens/s1. The blog reports about 12 tokens/s for a 70B 4-bit model on a Mac Studio M2 Ultra, or 53% of the ceiling1. This bound ignores KV-cache reads, attention compute and framework overhead1.

Weights are not the only resident data: in the vLLM paper's layout for a 13B model on an NVIDIA A100 40GB, parameters take about 65% of memory and the KV cache close to 30%, with the figure labelled above 30%3. For OPT-13B the paper gives about 800 KB of KV cache per token, so one 2048-token request can need 1.6 GB3. The blog adds a KV-cache budget of 5–15 GB depending on context length, plus 30% headroom1.

Quantization: trading bits for bytes, and what it costs on code

Quantization stores each weight in fewer bits, and the simplest form is uniform round-to-nearest (RTN), which picks a step size and maps each weight to the nearest level on a fixed grid2. For \(b\)-bit symmetric RTN with zero-point 0, the step is \(\Delta = \max(|W|)/(2^{b-1}-1)\), each weight is stored as \(\text{round}(W/\Delta)\), and it is recovered as \(\Delta \cdot \text{round}(W/\Delta)\)2. Rounding bounds each weight's error by half a step, \(|\delta| \le \Delta/2\), so one outlier that inflates \(\max(|W|)\) enlarges the step for every weight in its group. Group-wise quantization gives each group of about 128 weights its own scale and zero-point, trading extra storage for local adaptation2. NF4 places its 16 levels at quantiles of a normal distribution, so more levels lie near zero where most weights sit, while FP4 spaces its levels uniformly in log scale2. Naive RTN degrades at low bits because it treats all weights alike, although a small fraction of weights matters much more to the output4. On OPT-6.7B at INT3 with group size 128, RTN raises WikiText-2 perplexity to 23.54 from 10.86 at FP164.

GPTQ quantizes weights column by column and adjusts the not-yet-quantized weights to offset each error, using second-order (Hessian) information25. The AWQ authors argue that this reconstruction can overfit the calibration set and distort features on out-of-distribution domains4.

AWQ observes that keeping 0.1% to 1% of salient weights in FP16 greatly reduces error, and that salience is better read from activation magnitudes than from weight magnitudes4. Let \(w\) be a weight, \(x\) its input activation, and \(Q(w)=\Delta\cdot\text{Round}(w/\Delta)\) the same RTN quantizer as above4. Scaling the weight by \(s>1\) and dividing the input by \(s\) leaves the product unchanged before quantization, giving \(Q(ws)(x/s)\)4. Assuming the expected rounding residual stays near 0.25 of a step and that \(\Delta'\approx\Delta\), the ratio of the scaled error to the original error is roughly \(1/s\), so the relative error of a salient weight falls with \(s\) without mixed precision4. This step rests on the two empirical assumptions and is an approximation, not a proof. Large \(s\) is harmful because it enlarges \(\Delta\) for other channels; on OPT-6.7B perplexity was best at \(s=2\) (11.92)4. AWQ therefore searches \(s = s_X^\alpha\) over \(\alpha \in [0,1]\) by grid search, where \(s_X\) is the mean activation magnitude per channel, and it uses no backpropagation4.

GGUF is a file format from the llama.cpp project rather than a quantization algorithm, and its K-quants use 256-weight blocks with 32-weight sub-blocks2. A Q4_K block takes 144 bytes for 256 weights, which is 4.5 bits per weight once scales and minimums are counted2. BitsAndBytes quantizes on the fly at load time with NF4 blocks of size 64 and needs no calibration2. QuIP# applies rotation-based incoherence processing, and AQLM uses vector quantization with learned codebooks5.

On LLaMA and Llama-2 at INT4 with group size 128, AWQ's WikiText-2 perplexities stay close to FP16, for example 5.60 against 5.47 for LLaMA-7B4. On one H200 GPU, the Jarvislabs blog reports Qwen2.5-32B-Instruct HumanEval pass@1 of 56.1% at FP16, 51.8% for AWQ, GGUF Q4_K_M and BitsAndBytes, and 46.3% for GPTQ, where pass@1 is the share of problems whose first generated solution passes all unit tests2. With 164 problems the standard error is about 0.039, and the blog covers one model on one GPU2. Afrin et al. compared six 4-bit methods (GPTQ, AWQ, QuIP#, AQLM, BitsAndBytes, GGUF Q4_K_M) on Qwen2.5-Coder-7B-Instruct and CodeLlama-7B-Instruct, using McEval and CoderEval with pass@15. Across benchmarks, 4-bit quantization largely preserved pass@1, AQLM matched or exceeded the full-precision baseline, and QuIP# produced the only significant correctness losses, notably on BigCodeBench-Python5. Security was unchanged, AWQ significantly increased Java maintainability issues with a medium effect, and the study covers 7B models, two languages, three benchmarks and one 4-bit precision5.

Inference engines and runtimes: what differs and why

An inference engine loads the model's weights and manages the key-value (KV) cache of past attention states, which it keeps in GPU memory while a request is served3. The engines discussed here differ along three axes: single-user latency versus multi-user throughput, the weight formats they read, and the hardware they target. At batch size 1 decoding is memory-bandwidth-bound, and compute sits idle while waiting for data1.

llama.cpp is an inference runtime that reads models stored in GGUF files, the quantized format the Jarvislabs guide describes2. GGUF files for large models often come split into multiple parts that must be merged before use2. Ollama is a local server that the reader can start and query with a single command, and it is the common local path the quantization study targets15. The quantization study loads its models through Hugging Face transformers, so its numbers do not measure either tool's speed5. vLLM stores the KV cache in fixed-size blocks that need not be contiguous, as an operating system pages virtual memory, and the authors report 2-4 times higher serving throughput than earlier systems on their workloads3. The Jarvislabs guide, a practitioner blog on one H200 with Qwen2.5-32B-Instruct and not a controlled study, reports that the Marlin kernel raised AWQ throughput from 68 to 741 tokens/s with the weights unchanged2. The same guide reports that GGUF ran at 93 tokens/s in vLLM and advises llama.cpp for GGUF models2.

MLX is Apple's open-source array framework, optimised for Apple Silicon and offered with C++, Python and Swift frontends6. LM Studio 0.3.4 added an MLX engine built on mlx-lm, Outlines and mlx-vlm, which can enforce JSON output by masking tokens that would violate a schema-derived regex6. LM Studio runs MLX and llama.cpp models behind one UI and an OpenAI-like local server, and it can load several models at once6. Its blog reports about 250 tokens/s for Llama 3.2 1B on an M3 Max, a vendor figure with no stated protocol6.

The hardware target follows the engine: MLX is optimised for Apple Silicon, while CUDA-based frameworks such as llama.cpp with CUDA and Ollama favour NVIDIA hardware1. The sources give little head-to-head benchmarking of engines and little on llama.cpp or Ollama internals. The LM Studio and vLLM material is docs-level or blog evidence rather than controlled measurement62.

Efficiency techniques: KV cache, mixture-of-experts, long context, speculative decoding

During decoding, each new token attends to the keys and values of every earlier token, so the engine stores them in a KV cache instead of recomputing them3. In the generation phase, the key and value vectors at earlier positions are cached, and only the new key and value vectors for the current iteration are computed3.

$$ M_{\text{KV}} = 2 \times L \times H_{kv} \times d_h \times T \times B \times b $$

Here \(L\) is the number of layers, \(H_{kv}\) the number of KV heads, \(d_h\) the head dimension, \(T\) the tokens per sequence, \(B\) the batch size and \(b\) the bytes per element; this form is my derivation from the per-token count, not a formula the source states. The source's worked example is for OPT-13B in FP16, where the per-token count is 2 (key and value vectors) × 40 (layers) × 5120 (hidden size) × 2 bytes, giving 800 KB per token3. Since OPT can generate sequences up to 2048 tokens, one request can need up to 1.6 GB of KV cache3. Earlier systems reserved one contiguous chunk per request for its maximum length, and only 20.4% to 38.2% of the KV cache held actual token states3. PagedAttention splits the cache into fixed-size blocks that need not be contiguous, with a block table mapping logical to physical blocks, as operating-system paging does3. The authors report 2-4× higher serving throughput across various models and workloads, with larger gains for longer sequences and complex decoding3. Most of this benefit comes from batching many requests, so a single-user local session gains little from paging alone; this is my inference, not a reported result.

A mixture-of-experts (MoE) model routes each token to a few expert sub-networks, so it has a total parameter count and a smaller active count per token7. Memory must hold all experts, so the footprint follows the total count, while the weights read per generated token follow the active count. On a 24 GB GPU an 80B model cannot keep all its weights resident: 80 × 10^9 × 4/8 bytes = 40 GB at 4 bits, which exceeds 24 GB before any cache is added. Qwen3-Coder-Next has 80 billion parameters, activates 3 billion per forward pass, and uses hybrid attention with MoE8. GLM-4.5 has 355 billion total and 32 billion activated parameters, and GLM-4.5-Air has 106 billion total parameters9. Qwen3-30B-A3B has 128 experts, of which 8 are activated per token, while Qwen3-14B and Qwen3-32B are dense models7. A large-memory Mac can hold the full set, and the 3B active count then governs per-token speed.

Hybrid attention mixes different attention mechanisms across a model's layers, and the sources do not name the specific mechanisms Qwen3-Coder-Next uses8. Qwen3 dense models list a 32K or 128K context length in the architecture table, with 32K for the two smallest models and 128K for 4B to 32B7. Long context is costly for local agents because the KV cache grows with every tool call and observation. RULER, a long-context retrieval benchmark, shows that Qwen3 in thinking mode slightly degraded at extreme lengths, which the authors attribute to thinking content interfering with retrieval7. The sources do not report measured 128K limits for agent runs.

The sources do not explain speculative decoding; the only mention is that GLM-4.5 adds a multi-token prediction layer to support it during inference9.

Using a local model in the editor and in agents

A local coding model serves three uses: autocomplete proposes the next lines at the cursor, chat answers questions about selected code, and an agent edits files and runs commands over many steps8. An agent scaffold is the harness that runs the model in a loop, issuing tool calls and reading their results until the task ends. Tool calling means the model emits a structured request to run a named function with arguments.

Fill-in-the-middle (FIM) is a technique where a model predicts the missing parts of a code block10. A left-to-right model sees only the text before the cursor, so FIM trains it to fill a gap using the text after the cursor as well. The Qwen2.5-Coder report implements FIM with the special tokens <|fim_prefix|>, <|fim_suffix|> and <|fim_middle|>10. File-level pretraining uses a maximum training sequence length of 8,192 tokens, with next-token prediction and FIM as objectives10. Repo-level pretraining extends the context to 32,768 tokens, using repository-name and file-separator tokens to concatenate files10. The report states that the model supports input lengths of up to 128K tokens10.

Repository context is the editor's counterpart of retrieval: the model sees only what is selected, so file choice matters as much as the model. In SWE-bench, the 'oracle' setting retrieves the files edited by the reference patch, an approach the authors call less realistic because an engineer may not know those files in advance11. The realistic setting instead uses BM25 sparse retrieval to fill a context limit with files11. The original paper reports that models struggle to localize the code to change as context grows11.

Devstral-Small is a dense 24B model tuned for agent scaffolds, evaluated with the OpenHands scaffold and only bash and file-edit tools12. Its authors describe it as fast and deployable on local devices, but this is their claim, not a measurement12. The Qwen3-Coder-Next report trained on many tool chat templates, and in its experiments SWE-bench Verified rose with template count at fixed data volume, an experimental result from the vendor8. Its authors also found that trajectories from one scaffold transferred poorly to another8.

A local-agent case study ran eight open-weight models on 20 longitudinal data-preparation tasks inside a closed local environment13. The agent used SmolAgents, which does not require a model with native tool-calling capabilities, so smaller open-weight models could run on consumer hardware13. Gemma 4 31B scored highest on balanced variable performance (85.9%) and completed 75% of tasks13. The weakest model's failures were silent: its scripts ran without warnings but contained recoding errors13.

How coding models are evaluated, and how big the gap to frontier models is

HumanEval and MBPP-style benchmarks focus on natural language-to-code tasks, so they overlook broader code capabilities14. Pass@1 is the fraction of problems for which a single generated program passes all tests14. These benchmarks saturate: fine-tuned open models scored well on HumanEval+ but poorly on LiveCodeBench, which the authors read as overfitting to HumanEval14.

LiveCodeBench addresses this with live updates: problems from LeetCode, AtCoder and CodeForces contests carry release dates, so a newer model can be scored only on problems released after its cutoff14. DeepSeek models dropped sharply on LeetCode problems released after August 2023, which the authors read as likely contamination14. Its scenarios are generation, self-repair, code execution and test output prediction, and Pass@1 correlates above 0.88 across them, although relative differences between models vary14.

SWE-bench gives a model a GitHub issue and a codebase, and the model must produce a patch that passes the repository's tests11. The original benchmark has 2,294 task instances from 12 popular Python repositories, and the best model at release, Claude 2, resolved 1.96% of issues with BM25 retrieval11. With an oracle setting that supplies the files edited by the reference patch, Claude 2 resolved 4.8%, a setting the authors call less realistic than retrieval11.

Later reports use variants such as SWE-bench Verified, a human-filtered subset of 500 instances, evaluated by GLM-4.5 with OpenHands, a scaffold (the agent loop and tool setup wrapped around the model), and a 128K context limit9. Qwen3-Coder-Next reports SWE-Bench Verified, Multilingual and Pro, each with the SWE-Agent scaffold, plus Terminal-Bench 2.0 and Aider8.

GLM-4.5 reports 64.2% on SWE-bench Verified, against 1.96% for Claude 2 on the original benchmark, though these are different subsets and scaffolds911. In GLM-4.5's vendor report it outperforms GPT-4.1 and Gemini-2.5-Pro on SWE-bench Verified, and Claude Sonnet 4 on Terminal-Bench9. These gap figures are vendor reports, and the sources give no independent replication of them.

How far can the numbers be trusted?

A benchmark score is a measurement taken under a specific setup, so the setup should be checked before two numbers are compared. Each claim below is labelled with one of three tags: measured means a result from an experiment the source reports, inferred means a conclusion the source's authors or this tutorial draw from such a result, and vendor claim means a figure or finding that a model's developer reports about its own model.

  • Contamination (measured): LiveCodeBench scores models only on problems released after each model's cutoff, because the DeepSeek model dropped sharply on LeetCode problems released after its cutoff14.
  • Contamination (measured, then inferred): the localization task asks a model to name the files a fix must touch, given only the issue text, and is scored on whether the named files match the ground truth15.
  • Contamination (measured, then inferred): Prathifkumar et al. report that two Claude models localized files on SWE-Bench-Verified far better than on BeetleBox and SWE-rebench when given issue text alone, and that the gap is about six times for all-ground-truth-file localization against BeetleBox15.
  • BeetleBox and SWE-rebench are other benchmarks built from popular open-source Python projects15.
  • The memorization explanation is the authors' interpretation of that gap (inferred), not a direct test of memorization15.
  • Self-reported scores (vendor claim): the GLM-4.5 report ran SWE-bench Verified with OpenHands, a 100-iteration limit, history truncation to a 128K context and temperature 0.69.
  • Agent setup (measured, vendor-reported): Qwen3-Coder-Next reports in its own experiments that training on one scaffold transfers poorly to another, with OpenHands-specialized training transferring badly to SWE-Agent8.
  • Variance (measured): in 584 runs on an XGBoost task, identical runs of one agent-model pairing varied more than the pairings differed, so a few runs ranked agents unreliably16.
  • Rule-breaking (measured): ten of 312 runs broke the task's data rules, and they included the seven highest scores; removing them lowered the best score from 0.8293 to 0.769516.
  • Quantization (measured in a separate study): quantizing a model changes its code-generation scores, so a score on a quantized copy needs its own check5.

Practical rules follow from these failure modes. Prefer fresh benchmarks whose problems postdate the model's cutoff, as LiveCodeBench does14. State the scaffold, step and context limits, and sampling settings with every score, since the same model's result depends on them9. Repeat runs and report the spread, because a few runs can misorder agents16. Report compliance beside quality, and reject non-compliant runs before choosing the best one16. Test on your own tasks, since in the same study a later-year holdout kept only about a third of the measured gain16.

Which open-weight coding models matter in 2026, and what fits where

The choice of open-weight coding model comes down to a few families, and each family matches a different hardware class. The first split is dense versus mixture-of-experts (MoE): an MoE model routes each token through only a few experts, so it activates only a subset of its parameters per token7. Memory is paid for total parameters in both cases, while per-token bandwidth is paid for active parameters.

For a single 24 GB GPU, the small dense models are the natural fit. The Qwen2.5-Coder series spans six sizes, from 0.5B to 32B parameters10. Devstral-Small is a dense 24B model with a 128k-token context, which its authors describe as fast and deployable on local devices12. At 4 bits, 24 × 4 / 8 = 12 GB of weights leaves room for the KV cache on a 24 GB card; this fit estimate is the writer's arithmetic, not a measured result.

For large-memory Macs, or a GPU plus system RAM, MoE models with few active parameters are the main option. Qwen3-Coder-Next has 80 billion total parameters, activates 3 billion per forward pass, and uses hybrid attention and MoE8. Qwen3-30B-A3B has 30 billion total and 3 billion activated parameters, with 128 experts of which 8 are active per token7. Because every expert must stay resident, an 80B model at 4 bits needs roughly 40 GB for weights, so it suits a large-memory Mac or server rather than a 24 GB card; this is the writer's arithmetic.

For servers, the large MoE models are the comparison points. GLM-4.5 has 355B total and 32B activated parameters, and GLM-4.5-Air has 106B total parameters9. The GLM-4.5 authors report 64.2% on SWE-bench Verified9. The sources do not cover DeepSeek-V3.2, MiniMax M2.1 or GLM-4.7 as deployable models; they appear only as comparison bars in the Qwen3-Coder-Next figure8. Gemma coder specifics are not covered by these sources.

Licensing is stated for two families: all Qwen3 models are released under Apache 2.0, and Qwen2.5-Coder is described by its authors as permissively licensed710.

The one local case study gives the most direct evidence for on-premise use. Eight open-weight models ran entirely on local infrastructure on 20 data-preparation tasks, and the best, Gemma 4 31B, completed 75% of tasks with 85.9% of 102 variables correctly derived13. The authors report that performance generally rose with parameter count, and that correctness was the main differentiator13. The study used R and a single agent responsible for interpreting metadata, writing code, executing it, and debugging errors13.

Local versus cloud: privacy, latency, cost, licensing

Local deployment is a trade-off with a decision rule, not a verdict. Governance requirements typically prohibit data transmission to external services, and locally deployable open-weight models keep sensitive data in the local environment13. At batch size 1, decoding is memory-bandwidth-bound, so a single user's tokens per second are set by how fast the hardware reads the weights1. The sources give no per-token cloud prices and only limited hardware prices. Local use has a fixed hardware outlay and no per-query cost13. The blog's energy figures are one of three correction factors in its total-cost step: at 8 hours of use per day and $0.15/kWh, three-year energy costs are about $400 to $500 for a Mac Studio and $1,000 to $1,400 for a GPU workstation1. The evaluated open-weight models were released under the Apache 2.0 license, and Qwen2.5-Coder is described as permissively licensed; the sources do not cover API terms1310. In a fully autonomous run, the best local model completed 75% of data-preparation tasks, and weaker models produced silent errors13. Identical runs of one agent and model varied more than the differences between pairings, so a few runs rank agents unreliably16. Human review is advisable with smaller models because silent errors can materially affect downstream results13. Choose local when governance forbids transmission and you can accept more review and repeated runs. Choose cloud when data may leave and peak capability or throughput matters more than control.

Summary and self-check questions

Memory feasibility depends on weights, the key–value cache and other runtime data, which the vLLM paper breaks down for a serving setup in which parameters take about 65% of GPU memory and the KV cache over 30%3. For single-user decoding, memory bandwidth provides a speed ceiling, not a guarantee1. Quantization reduces weight storage, but code accuracy needs testing5. AWQ identifies salient channels using activation statistics4. Mixture-of-experts models distinguish total parameters from those active per token8. Engine choice depends on hardware and supported formats6. Agent scaffolds also affect reported performance8. Benchmark trust requires checking contamination and repeating runs, not simply comparing headline scores1516.

  • For a hypothetical 32-billion-parameter model at 4 bits, would weights plus 6 GB of cache and overhead fit in 24 GB2?
  • If each token requires reading 16 GB at 800 GB/s, what is the bandwidth-only speed ceiling, and what does it omit1?
  • Why can AWQ's equivalent channel scaling reduce quantization error4?
  • Why does an 80B-total, 3B-active mixture-of-experts model still need storage for 80B parameters8?
  • What two failure modes could make SWE-bench Verified scores overstate practical ability1516?
  • How would you compare two agents while controlling scaffold, sampling, context, quantization and run-to-run variation1658?
