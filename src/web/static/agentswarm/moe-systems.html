Mixture of Experts as a Systems Problem: Routing, Expert Parallelism, and Why Experts Cannot Be Pooled

What an MoE layer is and the two parameter counts

A dense transformer block contains an attention block and a dense feed-forward network (FFN) that every token passes through1. A mixture-of-experts (MoE) layer replaces the dense FFN with several alternative feed-forward networks called experts, plus a learned router that selects a small subset of them for each token21. Attention usually remains dense in both architectures2. The MoE change is commonly applied to the feed-forward part of a transformer block because that part contains a large share of the model's parameters2. Routing is normally performed per token and repeats at every MoE layer, so two tokens in the same sentence can use different experts23.

For a token representation \(x\), the router scores each expert, keeps the top \(k\) experts, and combines their outputs using the routing weights: \(y = \sum_{i \in \mathrm{TopK}(x)} g_i(x)\, E_i(x)\), where \(E_i\) is expert \(i\), \(g_i(x)\) is its router weight, and \(\mathrm{TopK}(x)\) is the set of the \(k\) highest-scoring experts2. The router is typically a linear feed-forward network, and its parameters are trained together with the rest of the model13.

Total parameters include every expert stored in the checkpoint, while active parameters include the selected experts and the shared parts used for one token2. Model names such as 235B-A22B give approximate total parameters first and approximate active parameters second2. Total parameters set the memory needed, and active parameters set the compute per token3.

As a worked count, suppose one dense FFN has \(P\) parameters2. An MoE layer with eight same-sized experts stores about \(8P\) expert parameters2. If the router selects \(k\) experts, about \(kP\) expert parameters take part in the calculation for one token2. With \(k=2\), only \(2P\) of the stored \(8P\) are used, but that \(2P\) is still more expert compute than the original \(P\)-parameter dense block2. So MoE increases capacity without increasing per-token computation by the same factor as the stored parameter count2. Active parameter count is only an approximation of runtime cost, since attention, embeddings and the output head still run, and routing adds scoring, sorting and token movement2.

The FFN is made sparse because it holds a large share of the model's parameters2. The checkpoint still contains every expert, so all experts must be loaded and their memory counted, whether or not they fire often3.

The guiding systems questions of this tutorial are: how a router's top-k choice becomes token movement across GPUs, what that movement costs in bandwidth and latency, how load imbalance is controlled, and when the memory cost of storing all experts is worth the compute saved.

Routing, load balancing and capacity

A router is a small learned linear layer that scores each token against every expert4. With token representation \(x\), router matrix \(W_r\) and \(N\) experts, the logits are \(h(x) = W_r x\), and the gate value for expert \(i\) is their softmax, \(p_i(x) = e^{h(x)_i} / \sum_{j=1}^{N} e^{h(x)_j}\)4. For a top-k set \(T\) of selected indices, the layer output is the gate-weighted combination \(y = \sum_{i \in T} p_i(x) E_i(x)\), where \(E_i\) is expert \(i\)4. Switch Transformers routes each token to a single expert, so \(k=1\), which the authors argue reduces router computation, can at least halve each expert's capacity, and simplifies communication4. The gate value \(p_i(x)\) keeps the router differentiable even with \(k=1\)4.

Load balance matters in parallel terms because experts are split across devices, each holding its own unique parameters, and uneven dispatch makes certain experts overflow4. If the router sends most tokens to a few experts, the devices holding them become the bottleneck while the others idle (the tutorial's reasoning from the device layout). The authors report that an auxiliary loss was needed to encourage balanced load across experts4.

The auxiliary loss uses two vectors over the \(N\) experts for a batch \(B\) of \(T\) tokens: \(f_i\), the fraction of tokens dispatched to expert \(i\), and \(P_i\), the fraction of router probability allocated to expert \(i\)4. They are \(f_i = \frac{1}{T}\sum_{x \in B} \mathbb{1}\{\arg\max_j p_j(x) = i\}\) and \(P_i = \frac{1}{T}\sum_{x \in B} p_i(x)\)4. The loss is \(\mathrm{loss} = \alpha \cdot N \cdot \sum_{i=1}^{N} f_i P_i\), where \(\alpha\) is a coefficient added to the total model loss for each Switch layer4. Under uniform routing \(f_i = P_i = 1/N\), so \(\sum_i f_i P_i = 1/N\) and the loss equals \(\alpha\) (our arithmetic). The authors state that the loss is minimised under a uniform distribution, which encourages uniform routing4. The count \(f_i\) carries no gradient, but \(P_i\) is built from the differentiable gate values \(p_i(x)\), so gradients flow through the loss into the router (our reading of the equations). In the Switch experiments, with a high enough coefficient the loss ensured good load balancing, and dropped tokens were typically below 1%4.

Tensor shapes are fixed at compile time while routing is dynamic, so each expert processes a fixed number of slots, the expert capacity, given by \(\text{expert capacity} = \frac{\text{tokens per batch}}{\text{number of experts}} \times \text{capacity factor}\)4. A token routed to a full expert is dropped: its expert computation is skipped and its representation passes to the next layer through the residual connection4. Worked example: with 8 tokens and 4 experts, the base capacity is \(8/4 = 2\) slots per expert (our arithmetic). Suppose the router sends 4 tokens to expert 1, 2 to expert 2, 1 to expert 3 and 1 to expert 4 (an illustrative assignment, not from the sources). At capacity factor 1.0 each expert holds 2 slots, so expert 1 drops 2 tokens and the other experts carry 0, 1 and 1 empty slots (our arithmetic). At capacity factor 1.5 each expert holds 3 slots, so expert 1 drops 1 token and the other experts carry 1, 2 and 2 empty slots (our arithmetic). At capacity factor 2.0 each expert holds 4 slots, so no token is dropped, but experts 2 to 4 carry 2, 3 and 3 empty slots (our arithmetic). A larger capacity factor alleviates overflow but increases computation and communication, shown as padded empty slots4.

Router logits are converted from bfloat16 to float32 before the softmax, which the authors describe as a step for stability4. No-Token-Left-Behind routing adds a second stage: tokens that overflowed their first-choice expert are routed to their second-highest-probability expert, and the process can be iterated to leave virtually no tokens dropped4. Status: the capacity formula, the k=1 argument and the balancing-loss derivation are design rationale, while the sub-1% drop rate is an experimental finding from Switch experiments4.

Running an MoE across GPUs: expert parallelism, dispatch and combine

Expert parallelism is one of several ways to split an MoE model over a cluster1. In combined model and data parallelism, a batch of \(B\) tokens is sharded across \(n\) data partitions and feed-forward weights across \(m\) model partitions, with \(N=n\times m\) total cores4. Switch's partitioning figure lays out these strategies over grids of 16 cores, including expert-and-data and expert-model-and-data parallelism4. In expert parallelism, experts sit on different devices, so tokens are sent to the device that holds the expert rather than moving expert weights between GPUs1. In Switch's expert-and-data configuration, the number of data partitions equals the number of experts, so each core holds one expert4.

One MoE layer on a multi-GPU system runs in a fixed sequence of steps15.

  • First, the router scores each token against every expert and keeps the top-\(k\) experts, with their gate weights kept for the combine step15.
  • Second, tokens are sorted by destination expert; DeepSpeed-MoE uses a token-to-expert mapping table and cumsum-based IDs rather than a sparse einsum5.
  • Third, an all-to-all dispatch sends each token to the device hosting its expert, while each device receives the tokens for its local experts1.
  • Fourth, each device runs its local experts as a few larger matrix multiplications rather than several small ones1.
  • Fifth, a second all-to-all combine returns each expert output to the device where the token originated1.
  • Last, the outputs are un-permuted into token order and weighted by the gate values5.

The forward pass therefore has two all-to-all collectives per MoE layer1. The backward pass runs the same two collectives in reverse roles, since the DeepEP wrapper describes backward dispatch as a combine and backward combine as a dispatch6. Counting both directions, one training step uses four all-to-all exchanges per MoE layer16. Because each token is sent to \(k\) experts, traffic grows with tokens times hidden size times \(k\); this is the tutorial's reading of the dispatch pattern14.

PyTorch's design places experts within a node so that token routing uses NVLink for fast GPU communication1. DeepSpeed-MoE's hierarchical all-to-all reduces hops from \(O(p)\) to \(O(G+p/G)\), where \(G\) is GPUs per node and \(p\) total GPUs, at twice the communication volume; it helps small batches because those messages are latency-bound5.

Fixed capacity pads unused slots, wasting hardware, while overflow requires dropping tokens or another protocol4. MegaBlocks instead uses block-sparse matrix multiplication so experts can receive a variable number of tokens without dropping any1. Databricks reports scaling MoE training to over three thousand GPUs with PyTorch Distributed and MFU above 40%1.

Hybrid-EP implements dispatch and combine, combining NVLink and RDMA and pipelining fine-grained chunks to mask communication latency7. Minimising GPU streaming multiprocessor usage leaves more SMs for computation and overlap7. NVIDIA reports filling NVLink with eight SMs on eight H100 GPUs and 16 SMs on GB200 NVL36, testing random routing, hidden size 8,192, BF16 and top-\(k\) of eight7. Hybrid-EP supports FP8/BF16 dispatch and BF16 combine, preallocating worst-case registered buffers because routed token counts change each iteration7. Reported Megatron Core speedups are 14% over DeepEP for DeepSeek-V3 and 5.5% to 9.9% for Qwen 3 235B, depending on precision7.

DeepEP offers all-to-all dispatch/combine kernels, including FP8 dispatch, configurable communication SM counts and deferred epilogues for overlap6. Its experimental Hybrid-EP branch uses TMA instructions for minimal SM usage and larger NVLink domains6.

Why MoE trades memory for compute

Per token, an MoE layer computes only the experts its router selects, so the arithmetic follows the active parameter count rather than the stored one2. Take one dense feed-forward block with \(P\) parameters and an MoE layer with \(N\) same-sized experts and top-\(k\) routing: the stored expert parameters are about \(NP\), while the parameters used per token are about \(kP\)2. Memory, however, follows the total count, because every expert must be resident somewhere, so rarely used experts still occupy GPU memory3.

$$ \text{FLOPs per token} \propto N_{\text{active}}, \qquad \text{weight memory} \propto N_{\text{total}}, \qquad N_{\text{active}} \ll N_{\text{total}} $$

This arithmetic is only an approximation of runtime cost, because attention, embeddings and the output head still run, and routing adds scoring, sorting and token movement2. The quality-per-FLOP claim is experimental: in Switch Transformers, models with the same FLOPs per token reached a target quality faster than dense T5 baselines, with pre-training speedups reported as 7x+, a lower bound4. This is a measured result on the authors' benchmark, not a theorem, and the authors note that speed depends on both the algorithm and the implementation4. The parameter cost is real: Switch-Base has 10x more parameters than T5-large (7.4B vs 0.74B) yet does not match its quality across a wide range of downstream tasks5.

Training and inference stress the hardware differently. In training, batches are large, so experts receive many tokens per step. Load balancing is needed because routing can send most tokens to a few experts, which then become overloaded while others receive little useful training2. In inference the batch size is small, so latency depends mainly on the time to load parameters from main memory, which makes it memory-bandwidth-bound5. DeepSpeed-MoE observes that a model 10x larger than its dense equivalent could need 10x the achievable memory bandwidth for similar latency5.

DeepSpeed-MoE reports, on its own setups, that it gives up to 4.5x faster and 9x cheaper inference than quality-equivalent dense models, and that a trillion-parameter MoE can be served under 25 ms5. These are measured results of the authors' experiments, not general guarantees. Imbalance adds risk: without intervention the router favors a few experts, and all-to-all communication for moving tokens to experts can become a large part of training and serving time32.

Why experts cannot be shared or pooled between models

The argument in this section is the tutorial's own reasoning from the sources, not a result any source states outright. A Switch or MoE layer sits inside one model and takes as input the token representation that the model's own attention layers and embeddings produce4. The router produces logits \(h(x) = W_r \cdot x\) from the token representation \(x\), and a softmax over the \(N\) experts gives the gate value \(p_i(x)\)4. The layer output is the gate-weighted sum \(y = \sum_{i \in T} p_i(x) E_i(x)\), where \(T\) is the set of top-k indices and \(E_i\) is the i-th expert4. Because \(W_r\) has one row per expert, each row \(W_r[i]\) is a direction in hidden space, and the logit for expert \(i\) is the dot product of the hidden vector with that direction. Training fits these rows to the hidden vectors that one model actually produces, so the router encodes that model's coordinates. A second model trained separately has its own embeddings and attention layers, so the same concept appears at different coordinates in its hidden vectors. For example, if the first model's row \(W_r[1]\) scores high on the direction it learned for code tokens, a code token from the second model may score high on \(W_r[3]\) instead, so the first model's router sends it to an expert never trained for that input. Therefore two separately trained models have different representation bases, so one model's experts are not interchangeable with another's, and a router trained for one model cannot address the other's experts (the tutorial's inference). Branch-Train-MiX (BTX) branches copies of a seed model and trains each copy on its own data in an embarrassingly parallel way, so the experts share one initial representation8. The feedforward sublayers of the expert LLMs become the experts of one MoE module per layer, the remaining parameters such as self-attention are averaged, and MoE finetuning is then needed so that the router can learn to mix the experts8. Branch-Train-Merge lacks the MoE finetuning stage that learns routing, while sparse upcycling omits the stage of training experts asynchronously8. These are experiments on Llama-2 7B variants with three domains (math, code and Wikipedia) and four experts, one of which is the original Llama-2 7B8. Top-2 routing with load balancing gave a more uniform load across experts, while models without load balancing relied heavily on the Math expert8. BTX uses less than half the additional training compute of Llama-2 13B and performs better on expert domains, an accuracy-versus-compute comparison reported by the authors8. Sparse upcycling without expert training beats the dense and BTM baselines but not BTX at the same or larger compute budget8. For MoE finetuning the authors sampled the math, code, Wikipedia and Llama-2 7B data with probabilities 30.16%, 40.31%, 10.30% and 19.23%, and they did not test mixtures other than uniform sampling8. These results cover one model family at one scale, so they support pooling only within that setup and are not a general proof. The conclusion, which relies on the tutorial's inference about representation bases, is that experts can be shared only inside a family with a shared origin, plus further training that teaches a router to use them.

Decoupling that works (1): many LoRA adapters on one shared base model

Mixture-of-experts models add capacity by sending each token to a few experts, which couples the experts, the router and the all-to-all traffic inside one model. A different route to many specialised behaviours keeps one frozen base model and stores each specialisation as a small low-rank adapter9. Serving thousands of such adapters is a systems problem, and S-LoRA is a system built for it9.

For a pre-trained weight matrix \(W \in \mathbb{R}^{h \times d}\), with \(h\) the output dimension and \(d\) the input dimension, LoRA introduces the update \(W' = W + AB\), where \(A \in \mathbb{R}^{h \times r}\), \(B \in \mathbb{R}^{r \times d}\), and the rank \(r \ll \min(h, d)\)9. Counting parameters, the adapter stores \(hr + rd\) values, which for \(h = d\) and \(r \ll d\) is about \(2dr\), against \(d^2\) for a full square matrix. As a worked example with \(d = 4096\) and \(r = 8\), the adapter holds about 65,000 values against about 16.8 million for the full matrix, a ratio of roughly 256 to 1; this arithmetic is the tutorial's own.

Merging each adapter into the base weights creates multiple full weight copies and misses batching opportunities9. S-LoRA instead computes the \(xAB\) term on the fly, so the costly \(xW\) product is batched across all queries while each request's adapter adds a much cheaper product9. S-LoRA stores all adapters in main memory and fetches only those needed by the running batch to GPU memory9. Loading adapters of different sizes alongside growing KV caches causes fragmentation and I/O overhead9.

Unified Paging keeps KV cache and adapter weights in one memory pool with pages of \(H\) elements, so a KV cache of length \(S\) uses \(S\) pages and a LoRA weight of rank \(R\) uses \(R\) pages9. Custom CUDA kernels, MBGMM for prefill and MBGMV for decoding, batch adapters of varying rank on non-contiguous memory without padding9. The tensor-parallel strategy aligns LoRA partitions with the base model's Megatron-LM partitions, and the added LoRA communication is small because \(r \ll h\)9.

Adapters are selected per request by the user or application, not per token by a learned router, so no all-to-all movement of tokens between experts is needed. The tutorial's reading, not a stated result of the paper, is that adapters need no joint training with a router, which is why this approach avoids the coupling discussed for MoE experts.

The authors evaluated Llama-7B, 13B, 30B and 70B on several GPU settings, including a single A10G (24GB), a single A100 (40GB) and a single A100 (80GB), with synthetic workloads9. On a single A100 80GB, S-LoRA served 2,000 adapters at 7.61 requests per second for setting S1, while vLLM with merged weights ran out of memory beyond five adapters and PEFT reached 0.88 requests per second with five9. The paper reports throughput up to 4 times that of vLLM-packed for few adapters and up to 30 times that of PEFT9. These are the authors' measurements under their own setup and baselines, not independent verification.

Decoupling that works (2): routing queries between whole models

A different decoupling leaves the network intact and routes each whole query to one of several complete models, rather than choosing an expert for every token inside one model10. The motivation is a cost dilemma: routing every query to the most capable model gives the highest quality but can be very expensive, while smaller models save cost but may lower quality10. RouteLLM focuses on two models, a stronger, more expensive one and a cheaper, weaker one10. The router looks at each query and predicts the strong model's win rate on it, where a win means the strong model's answer is judged better than the weak model's, so a high predicted win rate signals that the strong model is needed10. The query goes to the strong model only if this predicted win rate exceeds the cost threshold; otherwise it goes to the weak model10. Each request is associated with a cost threshold that determines the cost-quality tradeoff of that request, and a higher cost threshold leads to lower cost but may lead to lower-quality responses10. The repository recommends calibrating the threshold on a sample of incoming queries, for example to send 50% of calls to the strong model, using the public Chatbot Arena dataset by default10.

RouteLLM exposes routing through a controller addressed by a model name such as router-mf-0.11593, so an existing client changes only its model field10. Routers are pluggable (mf, sw_ranking, bert, causal_llm and random), and the repository reports that routers trained on one model pair generalise to other pairs without retraining10.

The project claims that routing saves cost while maintaining quality, reporting that its trained routers reduce costs by up to 85% while maintaining 95% GPT-4 performance on MT Bench10. The tutorial's own reasoning, not a stated result, is that this approach suits unrelated candidate models and per-query decisions, but it gives no per-token specialisation.

Decoupling that works (3): agents that cooperate through text

A multi-agent system is a set of LLMs that each autonomously use tools in a loop, working together on one task11. In Anthropic's Research feature, a lead agent plans the research process from the user's query and uses tools to create parallel agents that search for information simultaneously11. The architecture is an orchestrator-worker pattern in which the lead agent coordinates the process while delegating to specialised subagents that operate in parallel11.

In the tutorial's reading, this is a decoupling because the components interact through natural language rather than shared tensors. Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator11. The tutorial's own reasoning, not a claim of the source, is that because no tensors pass between agents, they need no common weights, no shared hidden representation and no joint training, which is exactly what experts from different models lack.

In HPC terms this is task parallelism over independent searches, with one orchestrator distributing work to workers and collecting their outputs. Agents typically use about 4× more tokens than chat interactions, and multi-agent systems about 15× more tokens than chats11. In Anthropic's own analysis, token usage alone explained 80% of the variance in performance on the BrowseComp benchmark, which tests the ability of browsing agents to locate hard-to-find information11.

Research suits this pattern because its open-ended steps cannot be hardcoded, since the path depends on what is discovered during investigation11. The source notes that a task's value must be high enough to pay for the extra tokens, and that domains where all agents must share the same context are a poor fit today11.

The lessons below are engineering experience reported by Anthropic, not controlled experiments11. Early agents spawned 50 subagents for simple queries and distracted each other with excessive updates11. Because each agent is steered by a prompt, the source recommends frameworks that define division of labour, problem-solving approaches and effort budgets rather than strict instructions alone11. Small changes to the lead agent can unpredictably change how subagents behave, so production reliability depends on observability and tight feedback loops11.

Per-token MoE stores every expert, and when experts are distributed across accelerators, tokens move by all-to-all communication that can take a large part of training and serving time2. NVIDIA describes expert-parallel communication as essentially all-to-all, which is hard to implement because only top-k experts are active per token7. The tutorial's inference is that this cost favours a single large job on tightly connected GPUs; neither source states that. Branch-Train-MiX suits a family of models sharing a seed, where experts train without communication and routing is learned later, as reported on Llama-2 7B variants8. LoRA adapters suit many tasks or users on one base model, and S-LoRA reports serving up to thousands of adapters9. Query routing suits independently built models with a cost-quality trade-off, where RouteLLM's vendor-reported claim is cost reductions of up to 85% at 95% of GPT-4 performance on MT Bench10. Text-cooperating agents suit open-ended, heavily parallel tasks whose value justifies about 15 times the chat token use11. The failure-mode and when-to-choose mappings are the tutorial's synthesis from these sources, not results any single source states.

Summary and check-your-understanding questions

Per-token routing gives sparse compute, but every expert's weights must stay resident, so memory follows total parameters2. Expert parallelism moves tokens to the devices that own their experts and back, so each MoE layer incurs all-to-all communication7. Load balancing and expert capacity are the main systems knobs, because they decide how evenly work spreads across experts and how many tokens overflow. Tokens beyond an expert's capacity are dropped, and their representation passes to the next layer through the residual connection4. Experts are tied to the representation space of the model that trained them, so pooling them needs a shared origin, as in Branch-Train-MiX, followed by further training to learn routing8. Looser coupling, through LoRA adapters, whole-model query routing or text-cooperating agents, offers independence between components91011.
